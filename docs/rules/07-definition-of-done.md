# 规则 3：任务完成必须覆盖更新架构大纲

> 状态: v1.1  最后更新: 2026-11-04  生效范围: 所有任务（人 + AI agent）
> 关联文档: [ARCHITECTURE.md](../architecture/ARCHITECTURE.md)、[03-abstract-first.md](03-abstract-first.md)、[04-data-driven.md](04-data-driven.md)、[05-numeric-package.md](05-numeric-package.md)、[06-extensibility.md](06-extensibility.md)、[08-parallel-sessions.md](08-parallel-sessions.md)

## 1. 规则原文

> **规则3：任务完成后，需要覆盖输出更新架构大纲，方便后续需要时读取架构内容。**

### 1.1 为什么

- 工程空壳期，**架构只存在于文档里**。文档一旦落后，后续任务就会照着过期地图施工。
- 人和 AI 的上下文都会过期。**每任务一次的写入，是为了下一阶段的读取**。
- 本工程明确「不为写文档而写文档」：架构大纲是**施工图**，不是交付物介绍。它的读者是下一个接手的 agent。

### 1.2 一句话判据

> **本次任务的产出，能不能只靠 `docs/architecture/ARCHITECTURE.md` + 源码就重建？**
> 能 → 更新到位。不能 → 还没做完第 6 步。

### 1.3 红线（违反即任务不成立）

| 红线 | 说明 |
|---|---|
| ❌ 另建 `ARCHITECTURE_v2.md` / `ARCHITECTURE-new.md` / `架构大纲-新版.md` | **唯一真源只有 `docs/architecture/ARCHITECTURE.md`**，新内容就地覆盖对应章节 |
| ❌ 只在文末追加一段「本次完成 xxx」 | 那不是更新架构，那只是日志；必须改对应章节正文 |
| ❌ 留一个空变更日志 / 只写日期不写摘要 | 变更日志的每一行都必须让读者知道「什么形状变了」 |
| ❌ 文件头「最后更新」时间戳不动 | GS006 会按时间戳判断过期 |
| ❌ 改了结构但没改接口清单第 3 节 | 下一个 agent 会因为查不到接口而重复造轮子 |

## 2. 「任务完成」的 6 步检查表

> 复制下面整段到任务描述里，逐项打勾。**任何一项未勾 = 任务未完成**。
> 只有第 ⑤ 步能自动化，其余靠自觉 + 评审。

```text
===== Definition of Done 检查表（任务收工前逐项勾选）=====

[ ] ① 抽象先行（规则5）
    - 已在新代码里优先使用 ARCHITECTURE.md §3.2 的既有接口
    - 新增接口已登记进 §3.2 表格（含：职责 / 实现者 / 已落地? / 所属任务）
    - 没有「先搭临时结构、以后再说」的实现

[ ] ② 数值零硬编码（规则4）
    - 新增/修改的 .cs 里没有玩法数值字面量
    - 必须存在的结构性常量已用 // arch-ok: 理由 标注
    - GS005 自检：.\tools\check_architecture.ps1 无「新增」的 GS005 条目

[ ] ③ 扩展性走查（规则7「改几个文件」判据）
    - 用本文件 §3 的判据表逐条核对
    - 新增一个怪物 / 技能 / 子弹样式 / 特效分别需要改几个文件？答案都在上限内
    - 写下一句实测结论：「新增一个 X 需要改 N 个文件」

[ ] ④ 数据契约校验通过
    - 涉及数据的：Excel 表头/类型/外键/schema_version 校验全绿
    - 生成物自检通过（.tres 可解析、index 条目数一致、无孤儿文件）
    - 代码里没有直接读 .xlsx
    - 新增/改动表已按主题归位：characters.xlsx / combat.xlsx / presentation.xlsx / progression.xlsx
      （Sheet 名 = 表名；新增主题文件需在 ARCHITECTURE.md §4.3 追加一行）

[ ] ⑤ 架构守卫无 error
    - .\tools\check_architecture.ps1  退出码 0 且 ERROR=0
    - 若引入了 new warning，已在汇报中说明原因
    - 基线有变化时：.\tools\check_architecture.ps1 -UpdateBaseline（并说明理由）

[ ] ⑥ 覆盖更新 docs/architecture/ARCHITECTURE.md
    - 改对了对应章节正文（见 §4 的影响矩阵）
    - 变更日志追加一行（见 §5）
    - 文件头「最后更新」改为今天
    - 没有另建任何 ARCHITECTURE_v2 / 副本 / 分卷

[ ] ⑦ 合并到主线（规则8；仅在并行会话场景下适用，全部在 worktree 内完成 ①~⑥ 之后）
    - 本次会话的改动全部发生在 .worktrees/<会话名>/ 内，没有在 main 上直接改
    - .\tools\session.ps1 commit -Name <会话名> -Message "<会话名>: <一句话>"
    - .\tools\session.ps1 finish -Name <会话名>   （先 rebase 到最新 main，再 merge --no-ff）
    - 合并后在 main 上复跑：dotnet build + .\tools\check_architecture.ps1（两边各自绿 ≠ 合起来绿）
    - ARCHITECTURE.md 冲突按「保留双方章节 + 变更日志两边都保留」处理（见 08 文档 §7）
    - 合并成功后 .\tools\session.ps1 stop -Name <会话名> 清理
```

### 2.1 六步对应的规则 / 工具

| 步骤 | 对应规则 | 检查手段 | 失败后果 |
|---|---|---|---|
| ① 抽象先行 | 规则5 | 人工评审 + §3.2 表格 | 打回重做 |
| ② 数值零硬编码 | 规则4 | **GS005**（warning，会有新增条目） | 打回重做 |
| ③ 扩展性走查 | 规则7 | 人工评审 + §3 判据表 | 打回重做 |
| ④ 数据契约 | 规则4 | pipeline 校验点 ①~⑤ | 构建中断 |
| ⑤ 守卫 | 规则1/2/3 | `check_architecture.ps1`（GS001~GS007） | **硬失败** |
| ⑥ 架构大纲 | 规则3 | **GS006** | **硬失败**（判定过期） |
| ⑦ 合并到主线 | 规则8 | `tools/session.ps1`（commit/finish/stop）+ 合并后复跑 ⑤ | 主线不健康时**回滚该次合并** |

> **⑦ 是「会话外壳」，不是第 7 个检查项**：①②③④⑤⑥ 管的是**这次任务做对了没有**，⑦ 管的是**这次改动怎么安全地回到主线**（[规则8](08-parallel-sessions.md)）。
> 单人单会话开发时 ⑦ 不适用；**只要有第二个会话在并行，⑦ 就是硬性的**。

## 3. 第 ③ 步详解：扩展性走查判据

引用 [06-extensibility.md](06-extensibility.md) 的「改几个文件」判据，收工前必须**实测**而不是估计：

| 扩展场景 | 可接受上限 | 走查方法 |
|---|---|---|
| 新增一个**怪物** | 0 个代码文件（纯 Excel 加行 + 生成） | 在 Excel 加一行 → 重新生成 → 能刷出来吗？ |
| 新增一个**技能实例**（已有技能种类的组合） | 0 个新代码文件 | 只改 `Skills.xlsx` 能装配出来吗？ |
| 新增一个**技能种类** | 1 个新文件（实现 `ISkill`） | 是否为它改了 Combat 的结算逻辑？改了 = 违规 |
| 新增一种**子弹样式** | 0 个代码文件 | 是否为它改了 `Projectile` 逻辑？改了 = 违规 |
| 新增一种**特效** | 0 个代码文件 | 只加 `Effects.xlsx` 一行 + 资源，能播吗？ |
| 新增一个**伤害修正**（如暴击、元素克制） | ≤ 1 个文件（`IDamageModifier` 实现 + 数据注册） | 是否改了结算主流程？改了 = 违规 |
| 新增一个**UI 面板** | ≤ 2 个文件（脚本 + 场景） | 是否引用了 `Game.Combat`？引用了 = 违规 |

**走查结论模板**（写在任务汇报里）：

```text
扩展性走查：
- 新增怪物「史莱姆王」→ 只改 data/excel/Characters.xlsx 一行 = 0 代码文件 ✅（上限 0）
- 新增技能「夺舍」→ SkillDef + 组合既有 ISkill，0 新代码文件 ✅（上限 0）
- 新增伤害修正「破甲」→ 1 文件 ArmorBreakModifier.cs ✅（上限 1）
```

**判据的意义**：如果任何一个数字超了上限，说明**抽象没做够**（规则5 没执行），应该回去补抽象，而不是把这次的实现交付出去。

### 4.2 强制字段（每个章节的写法要求）

每个章节都按四段式写，**缺任何一段即为不合规**：

```text
### X.Y 现状     ← 当前代码里真实存在什么（没有就写「未落地」，别写「已完成大半」）
### X.Y 目标     ← 要做成什么样（图画出来 / 表列出来）
### X.Y 约束     ← 不许做什么（红线 / 依赖方向 / 数据来源）
### X.Y 下一步   ← 谁来做、先做哪一步、做完回写哪节
```

### 4.3 「已落地?」列的处理

`§3.2 接口清单` 的「已落地?」列是**唯一可验证的进度指标**：

| 任务状态 | 该列的值 |
|---|---|
| 接口只在设计里 | ❌ 未落地 |
| 接口已写但无实现 | ⚠️ 仅定义 |
| 接口有 ≥1 真实实现且被调用 | ✅ 已落地 |
| 接口被废弃 | ~~已废弃~~（保留行 + 注明替代者） |

> 收工时：把本次落地的接口从 ❌ 改成 ✅，**填上任务名**。

### 4.4 绝不拆分的章节

以下章节**只能就地改，不能拆成子文件**：

- `§3 核心抽象与接口清单`（下一个 agent 查接口的唯一入口）
- `## 11. 变更日志`（GS006 用正则匹配含「变更日志」的二级标题，编号前缀可选，见 §5.5）
- 文件头的 `> 状态 / 最后更新 / 维护规则` 三行（GS006 从前 40 行内取第一个日期作为时间戳，见 §5.4）

> 若某章真的长到不可维护（例如 §3 超过 200 行），可以拆出 `docs/architecture/interfaces.md`，但**必须在原章节保留摘要表 + 链接**，且 `ARCHITECTURE.md` 仍是唯一入口。

## 5. 第 ⑥ 步的具体做法：就地覆盖，不是新建

### 5.1 正确做法（✓）

```text
1. 打开 docs/architecture/ARCHITECTURE.md（就是这一个文件）
2. 找到受影响的章节，直接改正文（Edit 模式，不要整篇重写）
   ├─ 把「未落地」改成具体内容
   ├─ 把「下一步」里已完成的那一行划掉或改成「已完成（任务名）」
   └─ 保持章节的 现状 / 目标 / 约束 / 下一步 四段结构
3. 在 `## 11. 变更日志` 表格末尾追加一行（见 §6）
4. 改文件头：
   > 状态: v1  最后更新: <今天 YYYY-MM-DD>  维护规则: ...
   （版本号只在「架构形状整体换代」时 +1，日常任务不动版本号）
5. 跑 .\tools\check_architecture.ps1 确认 GS006 不再报 stale
```

### 5.2 错误做法（✗）

| 错误做法 | 为什么不行 |
|---|---|
| 新建 `ARCHITECTURE_v2.md`，旧文件不动 | 两个真源 = 没有真源；下一个 agent 不知道该读哪个 |
| 新建 `ARCHITECTURE-2026-11-03.md` 归档 | 同上；历史在变更日志里，不在文件副本里 |
| 开 `docs/architecture/drafts/` 放草稿 | 草稿不是架构，架构只能有一种 |
| 在 `§12 待办` 里写「已完成」但不动正文 | 正文仍写着「未落地」，读者会照错的读 |
| 只改变更日志不改正文 | 日志说变了，正文没变 —— 这是最恶劣的情况（自相矛盾） |
| 直接删掉旧章节 | 删除架构形状必须说明「为什么删 / 替代者是什么」 |

### 5.3 版本号规则

| 情况 | 版本号 | 例子 |
|---|---|---|
| 日常任务（加接口、加 shader、调预算） | **不动** v1 | v1 → v1 |
| 架构形状整体换代（分层重排、语言栈切换、数据真源更换） | **+1** | v1 → v2 |
| 只有变更日志追加一行 | 不动 | — |

> 版本号在文件头 `> 状态: vN`，变更日志表格里也有「版本」列，两处必须一致。

### 5.4 时间戳规则（已与 `gs006` 新实现对齐，2026-11-03）

- 必须写成 `YYYY-MM-DD`（例：`2026-11-03`）。
- 放在文件头**第一块**的 `最后更新: ` 之后（常规写法：`> 状态: v1  最后更新: 2026-11-03  维护规则: ...`）。
- **GS006 的实际取法**（守卫脚本已修，比旧版宽松很多）：

| 项 | 新逻辑 |
|---|---|
| 扫描范围 | 正文**前 40 行**（旧的 25 行已放宽） |
| 扫描方向 | **从头部向下**，取**第一个**匹配到的 `YYYY-MM-DD` |
| 比较粒度 | **日粒度**——只要日期 = 今天，就不会报 stale |
| 取不到日期 | 若存在源码文件则报 stale（`no yyyy-MM-dd timestamp line in the header`） |

> **实操含义（比旧版简单）**：
> - 文件头正常写 `> 状态: v1  最后更新: <今天>` 就行，**不用**再刻意把日期行塞到第 25 行；
> - 唯一要小心的是：**不要把任何日期写进 `最后更新:` 那一行之前**（即第 1~3 行），否则它会成为「第一个日期」被取走。写在该行**之后**的日期（§0 表格、其它说明文字）都**不影响**判定 —— 守卫取到首个日期即停；
> - 变更日志（第 11 节）通常在 40 行之外，里面的日期**不会**干扰时间戳判定；
> - **`ARCHITECTURE.md` 前 40 行已核对：只有第 3 行一个日期**，可作为范本。

### 5.5 变更日志标题的写法（同样是 GS006 检查项）

- 标题必须是二级标题，含「变更日志」四个字。
- **编号前缀可有可无**，守卫用正则 `^##\s*(?:\d+[.、,)]\s*)?变更日志` 匹配，以下都合法：

| 写法 | 是否合法 | 说明 |
|---|---|---|
| `## 变更日志` | ✅ | 无编号 |
| `## 11. 变更日志` | ✅ | **本工程统一用这种**（与 §0~§10、§12 编号一致） |
| `## 11、变更日志` | ✅ | 顿号分隔也接受 |
| `## 11) 变更日志` | ✅ | 右括号也接受 |
| `### 变更日志` | ❌ | 必须是二级标题 |
| `## 附录：变更日志` | ❌ | 前缀不是纯编号，正则不匹配 |

## 6. 变更日志怎么写

### 6.1 表格结构（固定 5 列）

| 日期 | 版本 | 任务 | 变更摘要 | 影响文件 |
|---|---|---|---|---|
| `YYYY-MM-DD` | `v1` | 任务全名（与任务标题一致） | **一行一句话** + 分号分隔的要点 | 逗号分隔的路径列表 |

### 6.2 变更摘要的写法

**规则：一行一句话回答「架构形状变了什么」，不是「我干了什么」。**

| ✅ 好的摘要 | ❌ 坏的摘要 |
|---|---|
| `新增 StatPackage 分层与 StatCalculator；IDamageable 已落地` | `完成数值系统任务，写了 StatPackage.cs，修了几个 bug，顺便升级了日志` |
| `数据管线 MVP 接通：4 张 Excel 表 → .tres + index，校验点①~⑤生效` | `数据管线做好了` |
| `新增 hit_flash.gdshader；§7.3 shader 清单新增 1 行` | `加了个闪白效果` |
| `未改架构：仅调整 Characters 表数值与调参` | `调了一下数值` |

**要点**：
- 有具体章节/接口/文件名时**点名**（`§7.3`、`IStatProvider`、`hit_flash.gdshader`）。
- 改动了接口的形状 → 必须写「**破坏性变更**」字样。
- 一句能长到 2 行，但不要写成段落。

### 6.3 「影响文件」列怎么写

- 用相对路径，`,` 分隔：`scripts/data/StatPackage.cs, data/excel/Characters.xlsx`
- 同类文件可折叠：`scripts/data/**`、`shaders/*.gdshader`
- **必写**：本次新增/修改/删除的所有非忽略文件
- **不写**：`.godot/`、`data/generated/`、`obj/`、`bin/` 等生成物与缓存

### 6.4 一次任务的完整示例

```markdown
| 2026-11-05 | v1 | 战斗最小闭环：靶子 + 子弹 + 伤害结算 | 新增 IDamageable/IAttacker/IDamageModifier 并落地；§6.2 结算顺序 1~8 步跑通；§3.2 三接口改 ✅；§12 P1 两项完成 | scripts/combat/DamageResolver.cs, scripts/combat/IDamageable.cs, scripts/actor/ActorEntity.cs, scenes/debug/TestRange.tscn, data/excel/Weapons.xlsx |
```

## 7. 什么情况下 ARCHITECTURE.md **不更新正文**（但仍要留一行日志）

### 7.1 「不改架构」任务的判定

| 任务类型 | 是否改正文 | 是否留日志行 | 判定依据 |
|---|---|---|---|
| **纯美术资源**（模型、贴图、动画、音效） | ❌ 不改 | ✅ **必须留** | 没有新增/改变任何抽象、目录归位、数据表结构 |
| **纯数值调参**（Excel 里改伤害/血量/价格） | ❌ 不改 | ✅ **必须留** | 数值流入流水线，架构形状不变 |
| **纯 bug 修复**（不新增抽象、不改依赖方向） | ❌ 不改 | ✅ **必须留** | 修完架构还长原样 |
| **纯命名/注释/格式化** | ❌ 不改 | ✅ **必须留** | 同上 |
| 新增目录 | ✅ 改 §1 | ✅ | 目录结构是架构 |
| 新增 shader | ✅ 改 §7.3 | ✅ | shader 清单是架构 |
| 新增接口 | ✅ 改 §3.2 | ✅ | 接口清单是架构 |
| 引入新依赖 / 升级引擎 | ✅ 改 §0+§7+§9 | ✅ | 技术栈是架构 |
| 改动生成物 schema | ✅ 改 §4 | ✅ | 数据契约是架构 |

## 10. 常见问题

| 问题 | 回答 |
|---|---|
| 我只改了一行数值，也要改 ARCHITECTURE.md 吗？ | 不用改**正文**，但**必须**改文件头时间戳 + 留一行日志（§7.2）。 |
| 两个任务同时改 ARCHITECTURE.md 会冲突吗？ | 会。所以在任务描述里写清「预计影响章节」；冲突时按 §5.1 用 Edit 局部改，不要整篇覆盖。 |
| 我改了一个「待落地」的章节但还没实现怎么办？ | 写成 `⚠️ 仅定义` 或保留「未落地」，并更新「下一步」。**不许**写成已完成。 |
| 代码改了但实在不想动文档？ | 那就说明这个任务还没完成 —— 规则3 红线，且 GS006 会让守卫报 stale。 |
| 我能把 ARCHITECTURE.md 拆成多个文件吗？ | 见 §4.4：只能拆出子文件并在原章节保留摘要 + 链接，`ARCHITECTURE.md` 永远是唯一入口。 |
| 变更日志要删旧行吗？ | **绝不删除**。日志是历史，只追加。 |
| 发现 ARCHITECTURE.md 有错误怎么办？ | 直接修（就地覆盖），并在变更日志说明「修正 §X 的描述错误」。发现别人写错的不要在汇报里只提一句了事。 |
| 一个新任务的产出与 ARCHITECTURE.md 的「目标」冲突怎么办？ | 先找 Lead 仲裁；仲裁结果 = 更新 §X 的目标描述 + 变更日志注「目标调整」。**不要偷偷实现与文档不符的东西**。 |
