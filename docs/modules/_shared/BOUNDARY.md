## 2. 五大模块边界定义

### 2.0 判据（怎么判一份内容归哪个模块）

按下面三问依次判断，**第一个回答「是」的模块就是主归属**：

| 顺序 | 问题 | 判给 |
|---|---|---|
| Q1 | 这份内容**改了数值 / 表结构 / 内容投放**，玩家能感知到「不一样了」？ | **策划** |
| Q2 | 它描述**空间**（房间、地牢拓扑、装饰摆位、场景搭建）？ | **地编** |
| Q3 | 它描述**一个角色能做什么**（数值包组合、五槽技能、移动瞄准、HUD 显示）？ | **角色** |
| Q4 | 它约束**所有人怎么干活**（流程、目录、语言、构建、校验、文档纪律）？ | **开发** |
| Q5 | 它规定**代码结构**（实体/组件/系统/查询/命令、帧顺序、引擎边界、性能路线）？ | **ECS 架构师** |

> 兜底：问不出来 → 看它**服务谁的第一手工作**（规则 4 服务策划，规则 5/7 服务实现者，规则 3/8 服务所有会话）。仍判不出的，写进 §6 待核对项，交整合阶段裁决。

### 2.2 边界细则（In / Out / 交界处）

#### ① 策划 `planning`

- **In**：`data/excel/*.xlsx` 的**某一行 / 某一格**代表什么；`StatPacks` 五层怎么叠；`Objects` 一行 = 一个物件（武器/子弹/怪物同源）；`Tags` 十大轴与逻辑层/标识层；`SkillLoads` 五槽怎么填；`l10n.xlsx` 中文名；图鉴里的卡片为什么长这样；改完表要跑哪个生成器与校验器。
- **Out**：写 `*.cs`（哪怕是「只改一行」）；自己手改 `data/generated/`；决定某个数值该由哪条公式算出（那是 ECS/开发的 Modifier 层）；决定房间怎么排（地编）。
- **交界处**：
  - 与 **角色**：角色决定「字段有哪些、怎么组合」，策划决定「这格填多少」。角色 README 负责「加一个角色要动哪几张表的哪几格」，策划 README 负责「这张表每一列是什么意思、能填什么值」。
  - 与 **ECS**：组件里**不放** `Def` 引用（只存 `DefId`），所以「表里加一列」是否要改代码，判据来自 `ECS.md` §4.1 D1 与 `rules/04` §7。
  - 与 **地编**：装饰的收录与尺寸口径由地编维护（`decor_catalog.md`），策划只在需要新增装饰种类时提需求。

#### ② 地编 `level`

- **In**：房间与地牢（`ARCHITECTURE.md` §14）的四层切分 L1 词汇 / L2 规划 / L3 生成 / L4 表现；七类房型（Start/Combat/Special/Hidden/Prototype/Boss/Safe）；6 条可执行不变式；2D 栅格地图与调参面板（§14.8）；物件随机生成四类放置规则（§14.9）；训练房（§14.10）；**装饰目录**（`decor_catalog.md`：收录 101 条、层 `Ground/Wall/Ceiling`、`sizeRaw → sizeMeters → finalScale` 口径、跳过 200 条的原因）；相机跟随手感（§15.8，属于「看得见空间」的体验）；外观包 `VisualPacks` 里与**摆放体积**相关的部分。
- **Out**：写 `IDungeonPlanner` 的实现代码（那是开发/ECS）；决定数值（策划）；决定角色数值包（角色）；把 `素材/` 当运行时资源直接引用（**素材库是美术原料区，不是运行时资源区**，见 §17.10.1）。
- **交界处**：
  - 与 **角色**：外观包 `ModelPath` 的**归属权**在角色模块（`ARCHITECTURE.md` §17.10 唯一入口 `VisualPack`），地编只读它的**尺寸/摆位**含义。
  - 与 **开发**：`DungeonDebugScene` / `DungeonMap2D` 这类宿主场景的**接线**归开发，地编只描述「应该长什么样、怎么验证」。
  - 与 **策划**：房间可出什么装饰由「category 掩码」决定，那张表在 `config/decor_catalog.json`，地编是它的业主。

#### ③ 角色 `character`

- **In**：`ARCHITECTURE.md` §15 角色抽象（角色 = 五层数值包 + 一个技能包 + 两个标签的 ECS 组合；玩家怪物同源）；§18 第一个可玩人物 `test_hero` 全链路；§19 冲刺技能；§22 核心内容集 5 人物 / 5 怪物 / 5 武器 / 5 子弹；`design/character-hud-contract.md`（组件拼装 + 移动瞄准 + HUD + 变体，唯一接口约定）；**新增一个角色 / 一个技能要动几个文件**（`rules/06` 扩展预算的实操核对）；HUD 只读快照、不碰 ECS 的边界。
- **Out**：定义组件/系统本身（ECS 架构师）；决定角色数值具体填多少（策划）；决定相机与摆位体积（地编）；写渲染/特效 shader（开发）。
- **交界处**：
  - 与 **策划**：角色必须能说清「加一个角色 = 哪几张表加哪几行」，且**代码 0 行**（`rules/06` §2 预算）。
  - 与 **地编**：`VisualPacks` 的模型路径与缩放由角色定义口径，地编负责把它摆进空间。
  - 与 **ECS**：所有角色行为必须是 `SystemBase` 子类，不得出现 `class Player` / `if (kind == Player)`。

#### ④ 开发 `dev`

- **In**：`AGENTS.md` 的转述入口（开工 5 步 / 收工 4 步）；`rules/01` GDScript 禁令与 UI 层唯一定义；`rules/02` 语言选型 T1~T10 + H1~H6 下沉判据 + PS 5.1 编码陷阱；`rules/07` 完成定义 6 步与 `ARCHITECTURE.md` 的就地覆盖 SOP；`rules/08` worktree 并行与冲突处理；`prompts/QUICK-START.md` 与 `prompts/task-prompt-template.md`；`ARCHITECTURE.md` §1 目录契约（谁写谁读）、§2 分层依赖矩阵、§9 性能预算、§10 技术债；构建/守卫/测试工具链（`tools/check_all.ps1`、`check_architecture.ps1`、`env.ps1`、`session.ps1`）；**坑清单**（各章「踩坑记录」的汇总：静默失效、PS 编码、`.gdignore`、GDExtension Debug dll、viewer 描述符池……）。
- **Out**：改玩法契约（ECS）；改数值（策划）；改房间规则（地编）；改角色包组合（角色）。
- **交界处**：
  - 与 **ECS**：分层矩阵 `§2.3` 的判据在 `ECS.md` §3（`Game.Core.Ecs` 零 Godot 依赖），开发负责「守卫怎么查」，ECS 负责「为什么这么分」。
  - 与 **所有人**：`rules/07`/`rules/08` 是所有模块的**作业纪律**，任何模块收工都走同一套。
  - UI 层：GDScript 白名单与 HUD 两个话题的交界——「能不能用 .gd」归开发，「HUD 显示什么」归角色。

#### ⑤ ECS 架构师 `ecs`

- **In**：`ECS.md` 全文（§1 七条判定 J1~J7、§2 技术路线决策、§3 目录与归属、§4 数据模型/组件类别表、§5 内核 API 签名级契约、§6 一帧固定顺序、§7 引擎边界、§8 接缝、§9 性能四路线 + `IEcsBatchSolver` 契约、§10 测试、§11 变更纪律、§12 待办）；`ARCHITECTURE.md` §2.3 ECS 行、§3.2.0 ECS 侧已落地类型、§6.1.1 七步落进 ECS、§13 ECS 落地汇总（含 §13.5 踩坑）、§17 基础物件抽象（`ObjectArchetype` / `ValueRef` / `ForgeRules` / 位矩阵）、§20/§21 标签轴与逻辑层/标识层；`rules/03` §3.4 契约完备四问（**ECS 里「同类产物带同一套组件」的直接判据**）；`rules/05` 数值包折叠与值语义（组件侧实现口径）。

### 2.3 给五位负责人的使用说明（写 README 时按这个结构）

每人只需交付一个 `docs/modules/<模块>/README.md`，建议结构（可按实际调整）：

```
1. 这个模块负责什么（3~5 行，抄 §2.2 对应 In，不要更长）
2. 我必读的文档（表格：路径 · 章节 · 为什么读 · 行数，全部来自 §4 主归属 + §3 跨模块必读）
3. 我读一部分就够的（次归属，来自 §4）
4. 常见任务 → 该读哪一节（路由表，参照 rules/07 §8.2 的写法）
5. 我不管什么（抄 §2.2 的 Out + 交界处，避免越界改别人的东西）
6. 待核对 / 我没把握的点（交给整合阶段）
```

四条硬性要求：

1. **只增不改**：不得编辑 `docs/` 下任何原有文件（17 份之中除新增外一律不动），新增内容只写 `docs/modules/<你的模块>/`。
2. **不复制原文契约**：只做索引与路由，标题级引用 + 行号即可（例：`rules/04-data-driven.md` §5.2「表头四行规约」）。凡是需要精确签名/阈值的地方，写「原文见 …」，不要摘抄数字，避免两份真源。
3. **出处必须可点**：用 `../rules/04-data-driven.md` 这类相对路径（从 `docs/modules/<模块>/` 出发：`../../rules/...`、`../../architecture/...`）。

## 5. 只增不改的落地规则（本次全队必须遵守）

| # | 规则 | 检查方法 |
|---|---|---|
| 1 | **17 份原有文档一个字节都不改**（包括修正错别字、改链接、补目录） | `git status --porcelain docs/` 只应出现 `?? docs/modules/` |
| 2 | 新增内容只落在 `docs/modules/**` | 同上 |
| 3 | 本文 `BOUNDARY.md` 是基线，**模块负责人不得修改它**（发现问题写进自己 README 的「待核对」） | 整合任务最后统一裁决 |
| 4 | 不复制原文契约正文（签名、阈值、表结构），只写「章节 + 一句话 + 相对路径」 | 评审时 grep 模块 README 是否出现大段原文 |
| 5 | 链接一律相对路径，且**指向真实存在的文件** | 交付前逐个点开或 `ls` 校验 |
| 6 | 需要「改现有文档」的诉求（例如发现某节过时）→ 写进 `docs/modules/<模块>/README.md` 的「待核对」节或 `docs/modules/_shared/` 的汇总文件，**不直接改** | 整合阶段汇总后由人拍板 |

> 与 `rules/07` 的关系：`rules/07` 要求「架构形状变了就就地覆盖 `ARCHITECTURE.md`」。本次是**纯文档归纳、不改任何架构形状**，故按 `rules/07` §7「不改架构任务」的口径处理：`ARCHITECTURE.md` 可以只在变更日志留一行（由人决定何时留、要不要留），**绝不新建平行文档**。本次在 `docs/modules/` 下新增的索引文档不构成「ARCHITECTURE_v2」，因为它们不描述架构形状、只做导航。
